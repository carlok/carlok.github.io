---
title: "cdclkit 0.2.0: solvers answering for problems they no longer held, and 0.2.1 because the native wheels never shipped"
date: 2026-11-09
tags: [tool]
---

[cdclkit](https://github.com/carlok/cdclkit) released 0.2.0 on 9 November as a minor bump for the opposite of the usual reason — code that used to run now raises, and most of what raises was quietly getting a wrong answer. The worst was on the command line: `solve --preprocess --adaptive` printed a model of the *reduced* formula, so `(x1)` came back `s SATISFIABLE` with `v -1` and exit 10, because the adaptive branch returned before the only `pre.reconstruct`; every route now reconstructs before checking or printing, and `--self-check` evaluates a model against the input before reporting SAT instead of looking only at refutations. Two more were models outliving their problem: `Model.solve` rebuilt its solver only when a *variable* had been added, so `add(x != first)` could still return `first` and `add(x == 3)` could return `x = 4`, and `Model.solutions` left its blocking clauses on the shared solver, so a later `solve()` answered None on a satisfiable model.

The campaign's other findings are mostly refusals where something used to compile into a different statement: a Python `True` in a model constrained variable 0 (it is the int 1, read as a literal), `pyeq` compiling `and`/`or` in a value position to 0 or 1 so that `x or 5` was proved equal to `1`, decorators ignored so a function wrapped with `functools.wraps` proved equal to its undecorated self, a width of 0 or below proving anything equivalent to anything, and `Config` letting a seed of `2**32 + 1` work on one engine and fail on the other. A failed or interrupted solve could also poison every later answer from the same `Solver` — `MUSExtractor` then returned a satisfiable set and `verify` endorsed it — so a `Solver` a call was cut short on now says so through `Solver.broken`, and `solve`, `add_clause` and `new_var` raise `RuntimeError` on it.

Use 0.2.1, not 0.2.0, if you want the native engine: `cdclkit-native` 0.2.0 was never published, because GitHub retired the macOS image its wheels were built on and the release stopped after `cdclkit` 0.2.0 reached PyPI, so `cdclkit[native]==0.2.0` cannot be installed — and `cdclkit-native` 0.1.7 and earlier embed a checker that accepts refutations of satisfiable formulas. Wheels are built on `macos-latest` now; 0.2.0 also requires [dratify 0.1.11](/blog/2026/11/09/dratify-0-1-11-deletion-of-a-reason-clause/), and nothing else changes between the two versions ([0.2.0](https://github.com/carlok/cdclkit/releases/tag/v0.2.0), [0.2.1](https://github.com/carlok/cdclkit/releases/tag/v0.2.1), [3a1f880](https://github.com/carlok/cdclkit/commit/3a1f880)).
